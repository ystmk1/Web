# 깃부터 배포까지 협업 흐름

## 질문
> Git, GitHub, 브랜치, 호스팅 같은 개념이 각각 무엇이고, 어떤 순서로 이어지는지.

## 답

### 한 줄로
내 컴퓨터에서 [[깃]]으로 기록하고, [[깃허브]]에 올려서 같이 보고 합치고, [[버셀]]이 그걸 가져가 인터넷에 공개한다.

### 세 장소로 나누기
| 장소 | 하는 일 | 개념 |
|---|---|---|
| 내 컴퓨터 | 코드를 고치고 기록을 남긴다 | [[깃]], [[저장소\|로컬 저장소]], [[커밋]], [[브랜치]], [[깃이그노어]] |
| 깃허브 | 기록을 올려 두고, 같이 보고, 합친다 | [[깃허브]], [[저장소\|원격 저장소]], [[풀 리퀘스트]], [[병합]], [[포크]] |
| 버셀 | 코드를 가져가 빌드해서 공개한다 | [[버셀]], [[빌드]], [[웹 호스팅]] |
| 사이를 잇는 것 | 장소 사이에서 주고받는다 | [[클론]], [[푸시와 풀]] |

### 흐름 (워크숍 기준)
```
1. 클론        깃허브 저장소를 내 컴퓨터로 복사 (처음 한 번)
2. 풀          main의 최신 상태 받기
3. 브랜치      새 갈래 만들기 (예: login-page)
4. 코드 수정   AI와 같이 고치기
5. 커밋        기록 남기기 (한 줄 한국어 메시지)
6. 푸시        내 브랜치를 깃허브에 올리기
                 └▶ 버셀이 미리보기 주소를 만듦
7. PR          main에 합쳐 달라고 요청, 미리보기로 확인
8. 병합        main에 합치기 (충돌이 나면 골라서 해결)
                 └▶ 버셀이 main을 빌드해서 실제 사이트에 반영
```

### 헷갈리기 쉬운 점
- **깃 ≠ 깃허브.** 깃은 기록 프로그램, 깃허브는 기록을 올려 두는 웹 서비스다.
- **커밋 ≠ 푸시.** 커밋은 내 컴퓨터에만 기록한다. 푸시를 해야 팀원과 버셀이 볼 수 있다.
- **풀 ≠ 풀 리퀘스트.** 풀은 받아오기, 풀 리퀘스트는 "합쳐 주세요" 요청이다.
- **깃허브에 올리기 ≠ 사이트 공개.** 사이트가 열리려면 버셀 같은 호스팅이 빌드해서 띄워야 한다.
- **클론 ≠ 포크.** 클론은 내 컴퓨터로, 포크는 내 깃허브 계정으로 복사한다.
- **`.env`는 깃허브에도 버셀에도 자동으로 안 간다.** 깃이그노어로 막고, 버셀에는 [[환경 변수]]를 따로 넣는다.

### 웹 개발에서는
- 바이브코딩에서는 이 흐름의 대부분을 AI 코딩 에이전트에게 맡길 수 있다. "브랜치 만들어서 작업하고 커밋·푸시한 다음 PR 열어줘"처럼 말하면 된다. 다만 PR의 미리보기를 직접 보고 병합 버튼은 사람이 누르는 것이 안전하다.
- 이 위키 사이트도 같은 흐름으로 만들었다. 노트는 옵시디언 동기화로 깃허브에 올라가고, 사이트 코드는 브랜치와 PR로 `main`에 합쳐지고, 버셀이 자동으로 다시 빌드한다.
